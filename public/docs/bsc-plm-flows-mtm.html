Section 01

Purpose and how to read

This is the build and test companion to the MTM PRD. The PRD says what the product is and why; this document says, for every job a person does in the MTM edition, exactly what they click, what they see, what is saved, and how QA proves it works. It is written from the person's side, one flow per job.

Scope is the MTM edition only (VITE_EDITION=mtm). Screens that exist only for ready-to-wear (RTW planning, analysis, sheet, stock health, what is selling, launches, the RTW tracker and analytics, RTW requirements, the warehouse portal, GRN list, RTW materials to factories) are hidden in this edition and out of scope here.

How a flow is laid out. Every flow has the same nine parts, in this order: an ID and title; who does it (role and the people named in the PRD) and where (sidebar entry, tab and URL hash); preconditions (the data that must exist); the steps, one row per user action with the exact control label, what the system shows or does (including the toast text), and the data it writes; validations and errors (each rule and what the user sees when it fails); alternate and edge paths; postconditions (what other screens now show); and QA acceptance cases written as Given, When, Then, at least one of them negative.

Labels. Control labels, filter names, columns, pills and toasts are quoted as the prototype shows them today. Where a prototype label uses a long dash, this document shows a comma in its place, because the document style allows no long dashes; the control itself is unchanged.

IDs. UF-PROD production, UF-UNIT the four unit desks, UF-FAC the factory merchandiser, UF-FAB the fabric master, UF-PO purchase orders and supply, UF-SRC sourcing, UF-DES design, UF-SW the swatch desk, UF-COM conversation, files and the bell, UF-RET RetailOS interfaces. QA cases are the flow ID plus a number, for example UF-PROD-05.2.

Source of truth. The prototype's code as it stands on the date above, read screen by screen. Where the code and the PRD say different things, this document follows the code and lists the difference under Open points at the end, so the team can decide which one is right before the build.

Section 03

The order lifecycle

An MTM order is always at exactly one stage. Each move is a scan or a desk action with who and when. The four desks sit between PP · planned and In production.

  • Order (punched). Taken at the store in RetailOS, with the order sheet. Pre-confirmed orders (measurement not done, on hold, payment pending) wait here until confirmed.
  • PP. Waiting for a factory. Inside the freeze window (2 hours, a setting) the order is held back so the store can still change it.
  • PP · planned. On a plan submitted to one factory. From here measurements and styling lock; only a logistics remark can change.
  • CAD, then Cutting, then Fusing, then Compiling. Each desk takes the order up and marks it done (or blocked with a reason). An order cannot skip a desk.
  • In production. Scanned out of the production unit to the factory. Allowed only once compiling is done. The main fabric's metres leave physical and reserved stock here.
  • In factory. Scanned in by the merchandiser. Aging after 5 days.
  • Out factory. Marked ready by the merchandiser (QC done at the factory).
  • RTS. Back at the production unit.
  • Fitting / shipping. Dispatched by shipping.
  • Delivered. Handed over at the store or by courier.
  • Cancelled. Possible before cutting; the reservation is released.
